# Control UI/API contract research: bounded report workers

Research date: 2026-09-23. Scope: current report-run API, run manager/executor boundary, configuration persistence, and dashboard UI. Repository evidence below; recommendations are labeled.

## Current behavior (evidence)

- `RunManagerOptions.reportExecutor` currently accepts projects plus runner dependencies; `ControlRunRecord` and `StartRunParams` carry config name/ETag, run type, and optional project ID, but no worker count. Manager exposes one `startRun`/active-run lifecycle. (`src/reporting/report-server-run-manager.ts:22-24,43-63,86`.) Per task context, one active control run is allowed; the report runner currently collects enabled projects sequentially with one browser and a report-root lock.
- `executeControlRun` checks the submitted config ETag against the current config, selects enabled report projects, validates their artifact directories, then invokes the report executor once with runtime environment. Auto-build uses a separate branch and executor. (`src/reporting/report-server-run-executor.ts:24-26,36-48,66-75`.)
- `POST /api/run` already gates mutations with `validateMutationRequest`, requires `configName`, `configEtag`, `runType`, validates run type and auto-build `projectId`, then calls `startRun` and responds 202. (`src/reporting/report-server-control-api.ts:76-110`.)
- Dashboard's Generate Reports handler calls `triggerRun(activeConfigName, etag, 'report')`; auto-build calls the same helper with `'auto-build'` and project ID. (`src/reporting/control-page/pages/DashboardPage.tsx:112-123`.) `ExecutionSection` only renders the run button; it disables it for dirty config or an in-progress trigger. (`src/reporting/control-page/components/organisms/ExecutionSection.tsx:5-27`.) `useRunPoller` owns the trigger signature and POST body. (`src/reporting/control-page/hooks/useRunPoller.ts:20-23,169-193`.)
- `useControlApi` adds `x-csrf-token` to mutation requests; server mutation validation checks the token, host, and content type. (`src/reporting/control-page/hooks/useControlApi.ts:52-73`; `src/reporting/report-server-control-security.ts:75-102`.) Config edits use `PUT` plus `If-Match`; the run request instead carries `configEtag` in its JSON and executor rejects a stale config. (`src/reporting/control-page/hooks/useConfigManager.ts:122-130`; `src/reporting/report-server-control-api.ts:39-41,89-90`; executor `:24-26`.)
- Project config is schema version 1 with optional `defaults`; adding a persisted config field would touch config types and validation, not just dashboard state. (`src/config/config-types.ts:55-58`; `src/config/project-config-project-validation.ts:16-20`; `src/config/project-config-schema.ts:19-20`.) Existing active-config selection already has guarded `localStorage` read/write helpers and handles unavailable storage. (`src/reporting/control-page/utils/config-selection.ts:44-68`.)

## Recommendation (contract)

1. Treat worker count as a report-run parameter, not project config. Add numeric JSON `workerCount` to report `POST /api/run`; range 1–4 inclusive, integer only, default 1 when omitted (backward compatibility). Export one server-owned `MAX_REPORT_WORKERS = 4` policy and mirror it in the UI; never trust the UI bound. Reject a supplied report value outside the range, fractional, string, `null`, or otherwise non-integer with 422 `INVALID_WORKER_COUNT`; do not coerce or silently clamp. The exact cap is a conservative product recommendation, not a measured repository limit; validate resource/provider quotas before raising it.
2. Resolve the default at the API boundary and snapshot it on the queued `ControlRunRecord`; later preference changes must not mutate an accepted run. Extend `StartRunParams`/record with `workerCount` and pass it only through the report executor's options (alongside existing runtime environment), aligned with the runner's executor contract. Keep the manager's one-active-run rule: worker count means concurrent projects inside one report run, never multiple control runs.
3. Keep auto-build unchanged: UI does not include `workerCount` for `'auto-build'`; API/manager/executor route continues using the existing auto-build path and ignores no new execution behavior. Report concurrency must not affect auto-build concurrency or submissions.
4. Persist the UI choice as a same-origin browser preference in `localStorage`, separate from the config document. Initialize to valid stored integer or 1; on valid user selection, update UI and storage. On malformed/out-of-range stored data or storage access failure, use 1 in memory. Do not save this preference via config `PUT`, alter config ETags, or mark the config dirty. This matches the existing guarded browser-preference pattern; it is per browser profile, not shared across browsers/users.
5. Add a labeled numeric control (`min=1`, `max=4`, `step=1`) to `ExecutionSection`; keep selected state/persistence in `DashboardPage` (or a tiny preference helper), pass a change callback down, and pass the selected value to `triggerRun` only from `handleRunReports`. Keep the existing dirty-config and in-progress disabling behavior. A changed worker preference takes effect immediately without config Save; a page reload restores it from localStorage. The submitted count is snapshotted by the server.

## Alternative comparison

- **Per-request + localStorage UI preference (recommended):** one API field and one browser preference; config JSON and current ETag/save/reload workflow stay unchanged. Old clients omit the field and retain serial behavior (1 worker). Preference is intentionally local to the browser.
- **Persist in schema-v1 config (not recommended for this request):** could make the value config-specific/shared, but expands `ProjectConfigDefaults`, validators, editor serialization, fixtures/examples, and save/reload/ETag conflict behavior. The setting then makes the config dirty and the existing Run button stays disabled until save. This couples execution capacity to project configuration and risks an unrelated setting change being blocked by config-save conflicts.

## Validation and lifecycle cases for implementation

- API: omitted count -> 1; accept 1 and 4; reject 0, 5, negative, fractional, string, `null`, and non-finite/non-number inputs with 422 before queueing. Preserve existing malformed/run-type/auto-build project-ID responses and CSRF/Host/content-type gate. Existing stale-config ETag check must still fail before execution.
- Run lifecycle: returned/queued run uses an immutable count even if the UI preference changes; second independent run remains disallowed while active; count only reaches report execution. An auto-build request runs exactly the existing path regardless of any extraneous worker-count field.
- UI: initial default 1; valid selection survives page reload; invalid/stale localStorage and blocked storage fall back to 1; report click sends selected value; auto-build click does not; config `isDirty`/Save and run-in-progress disabling remain unchanged.
- UI/API tests should assert observable requests/status and no run queued for invalid input, not just helper forwarding. Keep tests for min/max/default and auto-build non-effect; no broad suite/gates in this research task.

## Risks / unresolved question

The maximum of 4 is an initial bounded recommendation, not verified by a benchmark. Confirm the supported memory/browser/provider-quota envelope before shipping; default 1 preserves current resource use. Parallel execution can expose shared-browser/session or artifact-writer races; the runner implementation must own those guarantees. No other unresolved UI/API contract question.
