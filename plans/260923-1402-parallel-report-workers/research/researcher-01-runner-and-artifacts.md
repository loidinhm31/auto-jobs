# Runner and artifact research: bounded report workers

**Timestamp:** 2026-09-23 (Asia/Bangkok)  
**Scope:** One Generate Reports invocation; repository evidence limited to the assigned runner, project-runner, artifact-path, lock-owner, and sequential-runner test files. No external sources consulted.

## Findings and recommendation

- **Safe boundary:** parallelize the per-project calls inside `runConfiguredProjects`, not whole report runs. That function acquires one report-root lock, recovers/cleans the root, launches one browser, executes configured projects, closes the browser, performs final cleanup and manifest discovery, then writes one aggregate; the lock is released in its outer `finally` (`src/runner.ts:90-105`, `107-136`, `139-184`). Keep all root-wide work serial and keep the lock from before recovery through aggregate publication. Lock ownership has a heartbeat and token-checked release (`src/artifacts/report-root-lock-owner.ts:193-245`). This does not enable concurrent control runs.
- **Recommend a fixed-size async worker pool** over raw `Promise.all`: validate/resolve a positive bounded worker count, use at most `min(workerCount, projectCount)` loops, claim projects in config order, and store each result at its input index. Then materialize `outcomes` in config order. `Promise.all` over all project calls is unbounded; `Promise.all` over the fixed worker loops is fine, but its worker-completion order must not determine project-outcome order. A process-worker design is disproportionate: the work is browser/network I/O, the runner intentionally shares one in-process `Browser`, and Playwright browser/context objects are not a useful process boundary (`src/runner.ts:105-116`; `src/project/project-runner.ts:126-157`).
- **Preserve one browser, one context/page per active project.** The runner launches one browser; each `runProject` makes a fresh `browser.newContext()`, creates its own page, and closes its context in `finally` (`src/runner.ts:105-107`; `src/project/project-runner.ts:126-141`, `171-184`). Do not share pages/contexts between projects. `configureContext` runs once per created context, so custom implementations must not depend on serial invocation or mutate shared global state (`src/project/project-runner.ts:23-32`, `126-135`).
- **Keep per-project fault isolation.** The runner catches a rejected/throwing project executor and records a failed `unallocated` outcome, then continues (`src/runner.ts:107-127`). Keep this catch inside each scheduled item; one project failure must not reject the whole pool or cancel siblings. `runProject` already converts workflow/capture/publication failures to persisted failed outcomes when allocation succeeded, and bounds workflow and cleanup operations (`src/project/project-runner.ts:143-189`, `190-223`, `248-300`).
- **Keep the artifact lifecycle unchanged.** Each job stages and allocates under `{projectId}/{runId}`; per-project directories and leases make distinct project IDs the natural concurrent writers (`src/artifacts/artifact-paths.ts:180-203`). Do not run orphan cleanup while workers are active: initial cleanup precedes work; final cleanup runs only after all workers and browser close, followed by discovery and aggregate publication (`src/runner.ts:102-105`, `129-143`, `167-184`). Discovery must see all completed manifests before the single aggregate is composed (`src/runner.ts:141-180`).
- **Worker-count compatibility:** default to one worker to preserve current sequential behavior; cap effective workers at enabled project count. The configured count needs a clear positive-integer hard bound before browser launch. Its allowed maximum is a product/config contract, not derivable from these files.

## Approaches and trade-offs

| Approach | Assessment |
|---|---|
| Fixed async worker pool + indexed results | Best fit: explicit cap, config-order results, low overhead, one shared browser; workers continue after per-item failures. |
| `Promise.all(projects.map(run))` | Ordered result array, but starts every project at once and so cannot honor a bounded UI worker count. A semaphore could bound it, but adds scheduling machinery without advantage over a small worker loop. |
| Child/process workers | Reject: no CPU-bound need; browser ownership/contexts are process-local, and IPC would add lifecycle/error complexity or require multiple browser launches, conflicting with the requested single-browser boundary. |

## Races and invariants to protect

1. **Completion order vs configured order.** Current sequential `outcomes.push()` happens in config order (`src/runner.ts:107-127`); concurrent pushes would instead reflect timing, and aggregate projects are emitted from that array (`src/runner.ts:167-180`). Reserve result slots by input index; never append as tasks finish.
2. **Duplicate project identity can collide.** `enabledConfiguration` checks common browser and output root, not duplicate IDs (`src/runner.ts:35-49`). `runProject` derives a timestamp-based ID unless a suffix is supplied (`src/project/project-runner.ts:97-100`; `src/artifacts/artifact-paths.ts:148-160`); staging uses project ID/run ID and leaf allocation uses exclusive `mkdir` (`src/artifacts/artifact-paths.ts:87-95`, `180-185`). If the direct `runConfiguredProjects` API receives duplicate IDs, same-second runs without unique suffixes can contend for the same staging/report path. Verify normal config loading rejects duplicates or reject duplicates before scheduling; do not assume parallel workers make this safe.
3. **Root-level cleanup/publication race.** Mid-run cleanup can see another worker's live staging lease or not-yet-published run; discovery/aggregate must not race active writes. Preserve outer lock scope and the current initial/work/finalize order (`src/runner.ts:97-104`, `139-184`; `src/artifacts/artifact-paths.ts:214-225`). Separate control runs remain serialized by the root lock.
4. **Browser lifetime and timeouts.** Do not close the browser, release the root lock, clean artifacts, or publish the aggregate when only some worker loops have settled. Per-project deadlines begin when `runProject` starts, with late context/page cleanup and bounded context/browser closure (`src/project/project-runner.ts:97-100`, `126-141`, `171-184`; `src/runner.ts:129-136`). A queued project should start its own project deadline when it takes a worker slot, not while waiting in the queue. A rejected item must still become an outcome so other items drain and finalization runs.
5. **Shared test callbacks.** The existing sequential test's shared `order` array records workflow entry and asserts strict order (`tests/unit/sequential-runner.spec.ts:169-199`); that observation becomes timing-dependent under parallelism. Keep outcome-order assertions, but assert a set/count for starts unless a test explicitly controls order. Its incrementing suffix callback is shared (`:184-193`) but runs in one JS event loop; avoid asserting which project receives a suffix based on racing completion. The test fake browser returns a new context object per call (`:51-55`). Tests use per-test temporary roots and remove them in `finally`; retain that isolation (`:169-172`, `:207-209`). The report-only selection test is single-project and continues to guard exclusion of auto-build projects (`:293-328`).

## Deterministic verification examples (proposed; not run)

1. **Overlap and cap:** use an injected `executeProject` with a deferred gate. Start at least four distinct project IDs, set effective workers to two, and have each executor increment `active`, update `maxActive`, signal when two have entered, then await an explicit release promise before decrementing. Before release, assert exactly two starts and `maxActive === 2`; release in a deliberately reversed order. Assert all four eventually start, `maxActive` never exceeds two, and returned outcomes remain in config order. Barriers, not sleeps, make overlap and cap deterministic.
2. **Failure isolation + finalize:** make one gated executor reject while another succeeds and a later project remains queued. Assert all configured projects receive ordered outcomes, the rejected one maps to the existing failed/unallocated shape, aggregate exit status reflects failure, browser closes once only after all work settles, then aggregate publication completes. Use a fresh temporary report/staging root.
3. **Real artifact overlap:** run real `runProject` calls through the existing executor seam with distinct project IDs, separate fake contexts, deterministic run IDs, and workflow/capture gates. After releasing both, assert each has its own report directory and manifest, no staging run directories remain, discovery includes both, and aggregate entries remain config-ordered. Include one workflow failure to check failed-manifest persistence and the other project's success.
4. **Lock/lifetime:** hold one worker at a barrier and observe that final cleanup/aggregate publication and lock release do not happen until release; verify browser closure follows worker settlement. Do not launch independent runs as a concurrency test; the requirement is intra-run only.
5. **Regression:** retain worker-count-one config-order behavior and report-only selection. Replace the existing strict workflow-start order assertion only where parallel mode is enabled; do not weaken the assertion that returned outcomes are ordered.

## Dependencies and unresolved question

- Runner/API work depends on the UI/config contract supplying one validated effective worker count; worker scheduling belongs only in report project execution after report-project selection (`src/runner.ts:187-195`). No auto-build selection change is needed.
- Unresolved: product must define the worker-count maximum (and confirm the UI/config-facing default). Recommendation here: default `1`; reject invalid/out-of-range values before browser launch or artifact-root side effects.
