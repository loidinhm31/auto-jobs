# Final individual report: control-only React viewer integration

## Recommendation

Keep disk-generated `/<project>/<run>/index.html` **unchanged, static, scriptless**. On `serve:control` only, intercept exactly `/reports/<project>/<run>/index.html` (and, if intended, the existing directory URL that resolves to it) and return the existing React control shell **after verifying that the corresponding persisted index exists through the existing safe report file opener**. Preserve the URL, use the existing `/assets/control-page.js` and `.css`, and render a report-specific React page there. Standalone report serving and direct opening of persisted HTML retain `REPORT_CSP` (`default-src 'none'`) and work offline. Do not embed the saved HTML, iframe it, relax `REPORT_CSP`, or add scripts to persisted files.

Viewer fetches `/reports/<project>/<run>/manifest.json` and `data.json` from the existing static handler; no new server data API needed. Decode and validate the pathname *once* using existing `decodeRequestPath`, require exactly three safe path segments (`project`, `run`, `index.html`), and match IDs against `SAFE_ID`; reject encoded separators, dot segments, double decoding and query variants as the current handler does. Route only `GET`/`HEAD` and do not make invalid/missing report URLs return a working shell. `openReportFile(reportRef.path, relativeDecodedPath, reportRef.identity)` plus closing its handle verifies the file and retains the report-root identity and Windows symlink/reparse-point protections in `report-server-file-io.ts:191-240`; `handleReportRequest` retains its own protections for JSON/screenshots. Keep host validation and `writeControlSecurityHeaders` for the shell. The static handler must remain the default for aggregate `/reports/index.html` (already control management route), `/reports/assets/report.css`, JSON, screenshots and every other report file; no global SPA fallback.

## Render path and trust boundary

1. New React `FinalProjectReportPage` reads only validated IDs from the pathname; fetch both same-origin JSON files with `cache: 'no-store'`, checks `response.ok`, parses as `unknown`, and runs `isValidManifestContract(manifest, {expectedProjectId, expectedRunId})`, then `isValidProjectResult(data) || isValidFailureResult(data)`. Require result/manifest project IDs, run IDs, state and identifying metadata to agree; reject inconsistent/missing inputs and show an error (no PDF action). Do not trust filenames or links from unvalidated JSON. `result-validation.ts:142-169,312-326` and `report-view-model.ts:97-117` already provide browser-safe validators/model building; imported runtime dependency graph (`config-errors.ts`, `config-selectors.ts`, `artifact-identity.ts`, `url-policy.ts`) uses plain JS/URL, not `node:*`. Do **not** import `report-output.ts`, `report-server-control.ts`, `report-server-files.ts`, `report-server-file-io.ts` or Node `fs/path/Buffer` into Vite browser code.
2. Call `createProjectReportViewModel` on validated inputs. Extract/export a narrowly scoped `renderProjectReportSections(model)` from `project-report-renderer.ts` composing existing escaped `renderJenkinsSection`, `renderSnykSection`, `renderSonarqubeSection`, `renderArtifactSection`; have `renderProjectReport` call the same sections function, retaining generated on-disk content. React page owns its header/footer and the PDF action, not a copy of four substantial evidence sections. Render **only the generated string from these trusted local renderer functions over schema-validated JSON**, never fetch/supply persisted `index.html`, vendor HTML or arbitrary JSON HTML as `dangerouslySetInnerHTML`. Audit interpolations and safe links when adding the sink: existing sections use `escapeHtmlText`/`escapeHtmlAttribute`, `safeExternalHref` with `target=_blank rel=noopener noreferrer`, and `localArtifactHref` checks manifest membership (`sections/*.ts`, `report-links.ts:14-33`). If project policy forbids *any* HTML-string insertion into the control DOM, instead convert these sections to shared React rendering components and use them for **both** persisted SSR and control UI; do not duplicate the four report sections.
3. Include `/reports/assets/report.css` for the report area, preserving existing classes/print styles. The existing relative screenshot/artifact links from section renderers resolve correctly when the document URL stays `/reports/<project>/<run>/index.html`; source links continue existing safe URL policy. Keep sections mounted and visible for capture (all Jenkins/Snyk/SonarQube/artifacts/warnings, including partial/failed runs); PDF export is an action on this final individual viewer, not on aggregate/history dashboard. Viewer styles must not accidentally hide evidence behind interactive tabs or scroll-container clipping.

## Exact change surfaces

- `src/reporting/report-server-control.ts`: add guarded exact individual-report interception *within* `/reports/` subtree after report root verification and before `handleReportRequest`; reuse existing shell HTML/HEAD and security headers. Validate route before sending privileged shell; ensure file handle closed. `src/reporting/report-server-file-io.ts` needs **no** change if `openReportFile` suffices; preserve its open/identity checks (`191-240`) and existing bounded static reads (`243-260`). `src/reporting/report-server-files.ts` supplies `decodeRequestPath` (`17-30`), existing static JSON responses and restrictive CSP (`57-91`); no broadened CSP there.
- `src/reporting/control-page/App.tsx:16-24`: route matching individual final report URLs to a new `src/reporting/control-page/pages/FinalProjectReportPage.tsx`; retain `/reports/index.html` -> `ReportManagementPage` and `/` -> `DashboardPage`; unexpected paths must not silently render dashboard. The PDF action integration belongs on this page.
- `src/reporting/project-report-renderer.ts:18-45`: share existing section composition without changing persisted HTML/CSP. New React page imports `createProjectReportViewModel` (`report-view-model.ts`) and existing `result-validation.ts`; no requirement to change these if browser bundle passes. If extracting top-level header as well, beware that the full renderer emits `<html>`, `<head>`, static report CSP meta, stylesheet and `<body>`: **never** inject that document into the control origin.
- Control HTML (`report-server-control-page.ts:42-45` and `control-page/index.html`) already substitutes escaped CSRF and Vite emits absolute fixed served JS/CSS paths; do not inject JSON into shell. `report-server-constants.ts:8-9`: preserve static `REPORT_CSP` and existing `CONTROL_CSP` (self scripts/styles/images/connect and frame-ancestors none). No inline scripts, `unsafe-inline`, `blob:` or iframe permissions needed for the viewer; PDF library CSP requirements are a separate integration decision.

## Consumer-visible acceptance/proof to include in implementation plan

- Control `GET` of final URL shows complete identical evidence from validated JSON; `HEAD` has no body. Direct persisted HTML and standalone static serving remain scriptless/offline, as does aggregate on-disk report. Existing control report history links continue opening the exact same final URLs.
- Missing index, invalid/double-encoded/traversal project/run, symlink/reparse-point swap, malformed/inconsistent manifest/data: no privileged evidence render/PDF action, and never a saved-HTML-to-control-DOM path. Static screenshots and JSON retain no-store and restrictive report CSP, shell retains control CSP and host checks.
- Compare success/partial/failed report headings, sections, anchor navigation, screenshot paths, artifact links, warnings and long tables between disk report and control viewer; browser-visible smoke must include a report with an actual screenshot and an actual PDF page capture (PDF ownership outside this slice).

## Unresolved questions

- Is the existing `/reports/<project>/<run>/` directory URL a required final-report entry point? Explicit requirement names `/index.html`; preserve any currently linked directory URL if users rely on it, with the same file-existence and ID checks.
- Confirm PDF library's external font/blob/data/worker requirements separately; no weakening of report/static CSP should be proposed merely to support export.
